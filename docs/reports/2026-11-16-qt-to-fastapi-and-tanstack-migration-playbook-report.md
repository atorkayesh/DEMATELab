# Migrating A Desktop Python App To FastAPI And TanStack Start In One Day: What Was Done And How To Repeat It

**Date:** 16 November, 2026
**Author:** Youpele Michael (with Claude Code)
**Scope:** The DEMATELab rebuild on branch `restructure/apps-api-web`, commits `df78b5c` to `1a13109` (base:
`cdc30ad` on `main`). Reference project for conventions: `/Users/youpele/DevWorld/FZJ/ice2kg` (secondary:
`/Users/youpele/DevWorld/FZJ/dac-atlas`). Written as a hand-off for an agent repeating this on a similar project.

## Summary

In one working session, a PySide6 (Qt) desktop app with no tests and no HTTP layer was restructured into a
monorepo with a **FastAPI API** (`apps/api`) and a **TanStack Start web app** (`apps/web`), Dockerised with
Compose, Nginx and a Makefile copied from ice2kg. The old app was moved, unchanged, to `qt-app/` as the
read-only reference. Everything the Qt app computes is reproduced by the API and proven equal by **135
frozen parity fixtures generated by running the Qt code itself**; the UI was redesigned as a Typeform-style,
one-question-per-step flow.

What made it work, in order of importance:

1. **Inventory before planning, plan before code.** Three parallel read-only research agents produced exact
   inventories (Qt logic, Qt UI, ice2kg conventions) with file:line references; two implementation-ready
   plans were written from them and reviewed by an independent agent before any code was written.
2. **Parity fixtures before porting maths.** The legacy code generated the expected outputs; the port was
   judged only against them.
3. **Copy conventions from a living sibling project** (ice2kg) instead of inventing structure.
4. **Parallel agents with disjoint file ownership**, a single coordinating session, and an independent
   review-then-fix loop at the end.
5. **The owner decided product questions; agents decided nothing material on their own.** Every
   deviation was reported back, not improvised.

End state: 144 API tests and 122 web tests passing, `make dev` serving web on `:3000` and API on `:50001`,
`make prod` healthy behind Nginx, 9 commits authored solely by the owner, nothing pushed.

## Questions

1. What exactly was done, in what order, and why?
2. Which decisions were made, by whom, and which defaults would apply to a similar project?
3. Which steps, prompts and checks can be reused as a playbook for another desktop-to-web migration?
4. What went wrong or nearly went wrong, and how was it caught?

## Findings

### 1. Starting point

| Aspect | Before |
| --- | --- |
| App | PySide6 desktop app (`DEMATELab/DEMATELab/*.py`, ~7,100 lines); Docker image served the Qt window over noVNC |
| HTTP API | None. GUI called Python functions directly |
| Tests, CI, lint config | None |
| Logic location | Mostly in GUI-free modules (`analysis_service.py`, `*_core.py`, `mmde_service.py`, `matrix_parsers.py`), **but** business rules hidden in GUI files: weight correction and name checks (`gui_app.py:55-101,1922-1946`), summary numbers, XLSX export, heatmaps (`results_viewer_widget.py`), workbook-to-expert matching (`matrix_editor_widget.py:611-656`) |

Lesson: "the logic is already separate" was only ~80% true. The research pass that listed **every**
computation inside GUI files (Finding 3) is what made the port complete.

### 5. Architecture delivered

```text
apps/api/   FastAPI. routers/ (one statement per handler) → features/ (all logic, classes with
            constructor injection + shared instance) → services/ (I/O only: LLM providers) / utils/
            constants/ one file per area · models/ Pydantic · errors/ AppError subclasses
            tests/fixtures/{parity,imports}/ · assets/fonts/ (Inter) · Dockerfile.dev/.prod
apps/web/   TanStack Start. routes/ (/, /status) · components/{ui,general,page-specific/<page>}
            hooks/ services/ interfaces/ (Zod) utils/ constants/ store/ (Zustand) · Dockerfile.dev/.prod
qt-app/     Legacy app, unchanged, with its own Makefile and compose files
data/examples/   Sample workbooks
docker-compose-{dev,prod}.yml · nginx/ · Makefile · docs/{plans,decisions,reports,research}/
scripts/generate_parity_fixtures.py   Runs against qt-app; never imported by apps/
```

API endpoints (`/api/v1`): `health`, `is-alive`, `scales`, `weights/defaults`, `weights/normalize`,
`analysis`, `analysis/export/xlsx`, `analysis/charts/causal-diagram`, `analysis/charts/heatmap`,
`imports/matrix`, `imports/workbook`, `explanations`.

Rules enforced by tests: every code file ≤ 300 lines; `apps/api` never imports `qt-app`; API key never in
logs, error bodies, the web store or the query cache.

### 6. The parity method (the core of the port)

1. Before porting any maths, a script in the repo root runs **the legacy code itself** with its own locked
   environment: `uv run --frozen --python 3.13 --project qt-app/DEMATELab python scripts/generate_parity_fixtures.py`
   (`--frozen` so the legacy lockfile cannot change; `--python` pinned because the lock covered several).
2. It drives the real legacy code paths (including GUI helper functions) for every case × solver ×
   threshold method and writes JSON: request, every result field, derived values the viewer computes,
   summary order, clustering output or error message, numpy version. Import fixtures and the legacy app's
   own XLSX exports were saved too.
3. The API pins the **same** numerical library versions as the legacy lock.
4. Tests compare feature output and HTTP output with every fixture at `atol=1e-12` (no loosening without a
   recorded decision). Result: bit-exact on macOS, max 6.4e-14 difference on Linux.
5. Where the legacy output was itself unstable (singular matrix in fuzzy "all no influence"; exact ties in
   "strongest relation"), the case was scoped or the test accepted either tied value, and this was
   documented in `apps/api/AGENTS.md`, never silently tolerated.

### 7. Agent orchestration that worked

| Phase | Agent type | Brief essentials |
| --- | --- | --- |
| Research | general-purpose ×3, parallel, background | Read-only; exact values; file:line; "what to strip" |
| Planning | planner rules followed by the coordinating session; plan-reviewer agent | Plan must be "Ready for implementation": no open product decisions; review against the code, not the plan's own claims |
| Implementation | implementer ×2, parallel | Follow the plan exactly; no worktrees or branches; **disjoint file ownership** (backend: `apps/api`, root infra, docs; frontend: `apps/web` only); no git state changes; never commit; report deviations with evidence; run all checks |
| Mid-flight change | SendMessage to the running frontend agent + plan file updated first | The plan file stays the single source of truth |
| Deferred cross-area edits | Coordinating session | The frontend agent listed the exact root-file edits it was not allowed to make; applied after the backend agent finished |
| Review | review ×2, parallel | Compare with the plan **and** the legacy code; the frontend reviewer smoke-tested the real API on spare ports |
| Fix | code-consistency ×2, parallel | Numbered findings with file:line and the exact correction; re-run checks |
| Commit | coordinating session | Owner-approved grouping, detailed messages, owner as sole author |

Owner preferences that shaped the process: plan before implementation; no worktrees unless approved; at
most two implementation threads; fresh approval before every commit or push; no Claude attribution in
commits or PRs; separate commits per feature group with detailed messages.

### 8. Problems hit and how they were caught

| Problem | Caught by | Resolution |
| --- | --- | --- |
| Moving sample data broke the legacy compose mounts | Checking references after `git mv` | Two mount paths and `.gitignore` updated in the restructure commit |
| Prod Nginx would fail without the web service (Compose rejects a dependency on a disabled profile) | Plan review | `required: false` plus runtime resolver until web existed; removed afterwards |
| Wrong chart dpi in the plan (legacy ignored its own dpi when drawing on an existing axis) | Plan review against code | 100 display / 300 download |
| Ranking tie order, `mean(axis=2)` vs defuzzify for charts/clustering | Plan review | Specified exactly as the legacy code |
| Weight correction planned in the browser contradicted "no maths in the browser" | Plan review | New `POST /weights/normalize` |
| Ports 3000/50001 held by another stack (ice2kg) | `make dev` port check | Agents used temporary overrides/spare ports; owner later stopped ice2kg |
| Legacy and new dev stacks share Compose project name `dematelab-dev` | Backend implementer | Documented; rename proposed, not yet decided |
| Gemini client closed before the call (500), unwrapped network errors, no SDK timeout | Frontend reviewer's live smoke test + backend review | Client kept alive, errors mapped, `HttpOptions(timeout=120000)` |
| User-supplied Azure endpoint allowed requests to internal hosts (SSRF) | Backend review | https + Azure host suffix allow-list, 422 otherwise |
| Cluster heatmap colours did not match the legend (legacy bug) | Backend review | Fixed as a label/display fix, recorded |
| Enter submitted the unclamped stepper value; focus landed on hidden inputs; stale "answered" matrix steps | Frontend review | Fixed with tests |
| Contradictory dpi in the two plans | Frontend implementer | Followed the settled decision; plans corrected |

### 9. Reusable playbook (for a similar project)

1. **Investigate** (read-only): stack, entrypoints, where logic lives, tests, Docker. Answer the owner's
   question in chat; do not change anything.
2. **Restructure only**: new branch; empty `apps/api`, `apps/web`, `docs/{plans,decisions,reports,research}`,
   `nginx/`, `data/`; `git mv` the legacy app into `legacy-name/`; fix only the paths the move breaks;
   `.gitkeep` empty folders; commit after approval.
3. **Research in parallel** with the three briefs in Finding 3, adapted.
4. **Ask the owner** at most a few material questions (ports, runtime version, scope, look). Propose
   defaults from Finding 4.
5. **Write two plans** in the reference project's plan format: Settled Decisions, Known Legacy Behaviour
   Kept, API Contract, Target Layout, Phases (skeleton → parity fixtures → constants/models/utils →
   features → import/export/charts → integrations → routers → Docker → tests/docs), Risks/Gates, Testing,
   Acceptance, Plan Validity, Handoff. Frontend plan: Settled Decisions, Theme table, Parity Inventory
   (every legacy text), Target Layout, Phases, Acceptance.
6. **Independent plan review** against the legacy code; fold in every supported finding; status "Ready for
   implementation" only with no open product decisions. Commit the plans.
7. **Implement in parallel** with disjoint ownership; parity fixtures before maths; agents never commit.
8. **Review in parallel** (one per app, including a live smoke test on spare ports), then **fix in
   parallel**, then re-run every check yourself.
9. **Run the stack** with `make dev`; let the owner click through; apply UX polish directly in small diffs.
10. **Commit** in logical groups with detailed messages (owner as sole author), then ask before pushing.

Checklist for "done": all endpoints in `/api/docs`; parity tests green; `make check` green; both apps
start with `make dev`; `make prod` healthy behind Nginx; every legacy UI text accounted for; no file
over 300 lines; no imports from the legacy folder; docs, AGENTS.md and decision records match the code.

## Limitations

- **Not verified in a browser by an agent:** the 320 px layout, the summary PNG export in Safari/Firefox,
  and a side-by-side visual comparison with the Qt app. The owner started clicking through after
  `make dev`; no systematic manual QA was recorded.
- **AI providers** were tested with mock transports and one live call with a fake key; no real key was used.
- **HTTPS** is prepared but commented out in `nginx/nginx.prod.conf`; the AI feature must not be used on a
  server before it is enabled.
- **Compose project name clash** (`dematelab-dev` used by both `qt-app/` and the new stack) is documented but
  not resolved.
- Durations in the timeline are approximate (taken from agent run times).
- The branch is not pushed and not merged into `main`.

## Recommendations

- Before merging: run a manual QA pass of every step and results tab against the Qt app on the two
  `data/examples/` workbooks, check 320 px and the PNG exports in Safari/Firefox, and decide the Compose
  project rename (proposed: `dematelab-qt-dev` in `qt-app/docker-compose-dev.yml`).
- Before deploying: enable HTTPS in Nginx; set `CORS_ORIGINS` and an empty `VITE_API_BASE_URL` for
  same-origin production.
- For the next project: reuse Finding 9 as the plan of work, the briefs in Findings 3 and 7, and the parity
  method in Finding 6. Copy conventions from the newest sibling project rather than this report's file list,
  since conventions drift.
- Consider removing `qt-app/` in a separate commit once the web app has been accepted by its users.
